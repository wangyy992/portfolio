爱豆收集梦想生活

AI 驱动沙盒养成 · 设计说明

设计主张 「确定性模拟 + 生成式 AI」的分工线画在哪里，决定这类产品能不能长期运行。 本作把线画在：游戏掌管时钟和世界状态，AI 只负责演当下这一刻，并提出小幅改动。 凡是 AI 抢了游戏该管的东西、或状态只靠 AI 回显的地方，都是要堵的漏。 成本控制不是让每次调用更便宜，而是让大部分时刻根本不需要调用。

01分工线

参考 Stardew Valley 与 Tomodachi Life 的做法，本作确立了一条硬性分工：

游戏掌管时钟和世界状态；AI 只负责演当下这一刻，并提出小幅改动。

确定性层（游戏）生成层（AI）
持有天数、时段、地点、好感、关系、档期、需求、里程碑触发不持有任何状态
决定什么时候发生什么、发生了之后世界变成什么样这一刻的对话与场景怎么演
提出—好感的小幅增减、一句记忆、可选的社媒内容
可测试性可写单元测试、可回归不可预测，只能约束格式

这条线的实际检验标准很直接：如果 AI 某一轮完全失败，游戏状态会不会被破坏？ 在正确的分工下，答案是「不会，只是这一段对话质量差」。 第 08 节的审计就是在逐条排查违反这条线的地方。

02需求：不调 AI 的心跳

Tomodachi Life 类玩法的心跳是「角色主动冒出需求，玩家去满足」。 朴素做法是每个时段问一次 AI「她现在想干嘛」—— 12 位爱豆 × 3 个时段 × 每天，光是生成需求就会把成本打穿。

本作的做法是把这层完全交给确定性哈希：

具体做法

  • 需求的有无：hash(memberId|need|day-slot) % 100 < 45——约 45% 概率有需求。 同一个人、同一天、同一时段永远得到同一个结果，不需要存储，也不会因为重新渲染而变化。
  • 需求的类型：7 种（想吃东西 / 闲得慌 / 有心事 / 想要个东西 / 想让你牵线 / 想分享 / 心情很好）， 同样由哈希从加权池中选出。
  • 性格影响权重：用正则匹配角色的性格文本给需求池加权—— 写着「吃 / 美食 / 零食」的角色更容易饿，写着「累 / 焦虑 / 内耗 / 敏感」的更容易有心事， 「话痨 / 活泼 / 社牛」的更容易想分享。很轻的偏向，成本为零，但让每个角色的需求分布有辨识度。
  • 无需求时也有表情：头顶挂一个同样由哈希决定的心情 emoji，随时段轻微漂移。 让每个人头上总有点东西——这是 Tomodachi Life 的质感来源。
  • 优雅降级：「想让你牵线」需要一个牵线对象，没有候选时自动退化为「想分享」， 而不是报错或产生空指针。
判断

这是全项目最值得复用的一个决定。它把 AI 的角色从 「持续驱动世界」压缩成「玩家主动触发时演一段」。

效果是双重的：成本上，绝大多数时刻的 API 调用是零； 体验上，角色的需求在玩家点开之前就已经存在且稳定—— 你昨天看到她想吃东西，今天再看还是那件事， 这种一致性如果交给 AI 生成，反而很难保证。 确定性在这里不是性能妥协，是体验本身。

03年历与档期

一轮 = 游戏内一年，52 周 × 7 天。档期由哈希确定性排布，带小幅浮动：

档期时间玩法作用
📀 上半年回归预热 + 🎤 打歌期第 8–11 周起，共 4 周爱豆常在练习室 / 打歌 / 后台，相遇机会密集，关系爆发窗口
✈️ 巡演回归结束后 5–7 周，持续 3 周部分成员「在外地联系不上」，制造想见见不到的张力
📀 下半年回归 + 🎤 打歌期第 32–36 周起，共 4 周同上
🏆 颁奖季第 50–52 周年末大事件锚点，高光时机
其余淡季 / 私下期低密度日常，可快进

排布种子是团名 + 年份，所以：同一个团每次开局的档期一致（可预期）， 不同的团档期不同（有辨识度）。浮动范围只有 3–5 周， 既避免了「每次都一模一样」，又不至于让玩家无法规划。

判断

大事件确定而小事件随机，是这类长周期养成的通用解法。 确定的大事件让玩家一开局就能在日历上看见「回归在第几周」， 从而产生规划行为——前瞻性就是目标感。 而随机的小事件（热搜、偶遇、吃醋）负责让每一周的具体内容不重复。 两者缺一：全确定则乏味，全随机则玩家无法计划，只能被动接受。

04统一关系模型

玩家↔爱豆与爱豆↔爱豆共用同一套模型： { affinity, tension, flags }，关系名由数值推导而非直接存储。

条件推导出的关系
tension ≥ 65 且 affinity < 55交恶
tension ≥ 50 且 affinity < 45疏远
affinity ≥ 90已表白 → 恋人；有恋爱意图 → 深度暧昧；否则 → 挚友
affinity ≥ 75有恋爱意图 → 暧昧；否则 → 好友
affinity ≥ 60 / 45 / 25 / 更低朋友 / 普通认识 / 眼熟 / 陌生

两个设计点值得说：

  • 关系名是推导出来的，不是存的。 存的只有两个数值加若干 flag。这意味着关系永远与数值一致， 不存在「好感 92 但显示还是朋友」这类状态不同步的 bug。
  • 同一个 affinity 因「意图」不同而呈现不同关系。 好感 80 在恋爱意图下是「暧昧」，在朋友意图下是「好友」—— 玩家的定位选择直接改变关系的性质，而不只是速度。 这让「专一 vs 广撒网」成为真实取舍，而不是数值优化题。

爱豆之间的初始关系从各成员的 initialRelationships 播种； 配对键做了规范化排序（pairKey），保证 A-B 与 B-A 指向同一条记录。 「看着我撮合的两人真的成了」——这条玩家爽点之所以成立， 前提就是 NPC 之间的关系和玩家自己的关系用的是同一套可演进的数值。

05九种结构化输出块

AI 的回复是自然语言，但其中需要写回游戏状态的部分必须包在标记块里， 由代码解析后才生效。共九种：

标记块承载作用
SNAPSHOT好感小幅变化等强制，每轮必须有
RELDELTA爱豆之间关系的变化撮合玩法的数值出口
RISK风险提示状态预警
CARD卡片式内容结构化展示
KKTMSG手机私信虚拟社交平台层。
把「关系」外化成可见的社交痕迹
WEVERSE爱豆发的动态
BUBBLE私信订阅式消息
THEQOO论坛热帖
MUSICSHOW打歌成绩见第 08 节——这一块存在双源问题

格式要求写得相当强硬，例如：正文 60–140 字；结尾必须有 A. / B. / C. 三行具体选项， 不能写「你可以选择」，不能用数字编号；SNAPSHOT 是强制要求禁止省略。

一条容易被忽略的约束

prompt 里专门写了：「affection 只在本轮真的有实质进展时才变；敷衍 / 寒暄 / 被冷落就保持不变（+0）， 不要为了凑数硬加。」

这条很关键。生成模型有强烈的「让玩家开心」倾向， 如果不明确要求，它会在每一轮都给一点好感——于是好感变成时间的函数，而不是行为的函数。 一旦玩家意识到「随便聊也会涨」，所有对话选择就失去了意义。 在生成式养成里，「不涨」比「涨多少」更需要被显式设计。

06上下文与成本

第 02 节的需求系统已经把调用频次压到最低，剩下的是每次调用的体积控制：

手段做法作用
历史裁剪messages.slice(-10)只带最近 10 轮
剥离标记块 回传历史前，用正则把全部九种标记块从旧消息里删掉 关键一步——见下
分角色记忆memories[memberId].slice(-4)每个角色只带最近 4 条长期记忆
输出上限max_tokens: 4096，temperature: 0.75限制单轮体积

「剥离标记块」这一步值得单独说。AI 每轮输出里都含有 SNAPSHOT 等结构化块， 如果原样回传进下一轮的历史，会产生两个问题：

  1. 体积膨胀——这些块的 token 量不小，且随轮数线性累积。
  2. 模型会模仿历史里的块并「重放」旧数值。 它看到前面几轮都有 SNAPSHOT，可能把旧的好感值抄进新的一轮， 造成状态回滚。

剥离之后，历史里只剩纯粹的对话正文， 而真实状态由确定性层在上下文开头重新注入——数据只有一个来源。

07里程碑与结局

并非所有内容都交给生成。系统里保留了两类 authored（人工编写） 的节点：

里程碑：暗线积累后的重头戏

里程碑是好感积累到阈值后触发的大节点，由 milestones.ts 定义， 条件包括：最低好感、是否需要恋爱意图、是否需要「晚上 / 汉江 / 天台」这类能说心里话的时空。

与日常的碎片剧场相对，里程碑更长、更正式、有醒目预兆（世界里显示 ⚡）， 并会被记进大事记，最终喂给年鉴与结局。 这张表被 prompt 和世界视图共用——同一份定义既驱动生成，也驱动 UI 预兆， 保证「玩家看到的预兆」和「实际会触发的事」不会脱节。

结局：条件触发，玩家决定何时收

四类结局：恋人线、撮合线、见证线、BE。设计原则写在代码注释里：

结局的设计原则

「明确的 END 一直挂在那儿（有目标、可达成、可收口）＝ 收敛； 收不收由玩家定，日常甜蜜和随机事件可以一直玩 ＝ 不硬切。」

这解决了沙盒养成的一个经典矛盾：有结局则玩家被迫结束，没结局则努力没有回报。 本作的解法是把结局做成随时可用但不强制的收口—— 目标感来自「我知道能走到哪」，自由度来自「什么时候走由我定」。

08状态所有权审计

项目做过一次专门的审计，逐条排查「AI 抢了游戏该管的东西」的地方， 产出 13 条问题，分四类：时间/世界所有权、玩家能动性、状态可靠性、其它。

其中几条特别能说明第 01 节那条分工线在实践中会怎么破：

编号问题症状处理
F1 AI 自己跳时间 / 换场 旧 prompt 每 2 轮硬命令「结束场景 + 跳周」 已修：改为实时对话指令
F2 currentScene 有两个真相源 世界地图有 worldLocation，AI 又每轮用 SNAPSHOT 覆盖它。你在咖啡厅，AI 说练习室，顶栏和地图对不上 地点以世界为准，AI 不再覆盖
F3 两个时钟打架 叙事锚点用 turnCount（每回复 +1），世界时间是 worldDay/worldSlot（玩家推进）。聊 3 句 AI 就以为过了 3 段时间 时间锚点改喂「第 D 天·上午/下午/晚上」，并说明这一刻在对话里固定不变
F4 回归期由 AI 每轮说了算 本该由日历决定，AI 的 SNAPSHOT 每轮覆盖，与日历打架 以日历为准，从 SNAPSHOT 移除
F5 打歌名次双源结算 代码已在推进时段时算名次（对），但 prompt 仍允许 AI 输出 MUSICSHOW 块并被照单全收 → 一位可能被算两次、结果冲突 成绩由代码算，AI 只演旁白与获奖感言

F3 是这类系统里最隐蔽的一种 bug：两个时钟各自都对，合在一起就错。

它的隐蔽之处在于没有任何一处代码是写错的—— turnCount 用来做叙事节奏是合理的， worldDay 用来做世界时间也是合理的， 问题只出在「喂给 AI 的时间锚点用了前者」。 这类 bug 无法靠单元测试发现，只能靠一次专门的所有权审计。

方法本身值得复用

审计的判据只有一句：凡是 AI 抢了游戏该管的东西、或状态只靠 AI 回显的地方，都是漏。

按这句话把所有状态字段过一遍，问两个问题—— 「这个字段的真相源是谁？」「如果 AI 这轮胡说，它会被改坏吗？」—— 13 条问题就是这样找出来的。 任何把 LLM 放进主循环的产品都应该做一次这样的审计， 而且越早做越便宜：F2 到 F5 都是「已经写完才发现」的类型。

10已知问题与下一步

已知问题

  • 审计中仍有未修项。13 条里已修的只是一部分，F2–F5 等需要逐条落地。
  • App.tsx 达 2393 行。状态机、UI、AI 调度混在一处，继续加系统会越来越难改。
  • 打歌评分仍有双源风险（F5），在完全切到代码算分前，结果可能不一致。

下一步要验证的问题

  1. 需求系统的 45% 是不是合适的密度。 太高则玩家疲于应付、每个都点会很累；太低则世界显得没人在活动。 需要观察玩家实际点开冒泡的比例——如果远低于出现率，说明密度过高，反而稀释了每个需求的分量。
  2. 「好感只在有实质进展时才变」是否真的被模型遵守。 这是第 05 节那条约束的落地检验。做法是记录连续多轮敷衍对话下的好感曲线—— 如果仍在稳步上涨，说明约束没生效，需要改为由代码判定是否允许本轮加好感。
  3. 实测单用户成本。 第 02 节和第 06 节的所有设计都是为了压成本，但目前缺少实际的 token 消耗数据。 需要统计人均单次会话的调用次数与 token 量，才能判断这套架构在更大规模下是否成立。
